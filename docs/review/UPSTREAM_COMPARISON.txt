四、极化相关products：已发现继承的公式问题
GPU压缩双极化布局：
gridder.cuh:551-558先得到temp_data.x=(ReX,ImX)、temp_data.y=(ReY,ImY)，:575-578交换两个字段后成为RRII：
pix.x=(ReX,ReY)，pix.y=(ImX,ImY)。
这是cuFFTDx半精度两FFTs并行存储约定，fft_dx.cuh:92-102注释同样说明RRII。
设a=ReX,b=ImX,c=ReY,d=ImY：
- ComputeXX，cu_helpers.cuh:467-471：a²+b²，正确。
- ComputeYY，:487-489：c²+d²，正确。
- ComputeUU，:504-505：a*b+c*d，然而注释是Re(X*conj(Y))；数学正确公式a*c+b*d。因此这一公式与自己RRII约定不一致。
- ComputeVV，:521-522：c*b-a*d，等于Im(X*conj(Y))，正确。
本地仅为上述返回值增加float中转构造，未改UU公式；本地对应:480/498/516/534。
已用微小Python复数代数验证x=1+2j,y=3+4j，XY*=11+2j，而继承UU公式得14，VV得2。此验证不包含GPU布局变换，源码RRII布局证据如上；建议加明确RRII单测，随后谨慎修公式。
输出四个float实际为[XX,YY,候选ReXY*,ImXY*]，不是Stokes[I,Q,U,V]。函数命名UU/VV容易误导：即便修正UU，Stokes U/V还存在常见2倍/符号约定，要遵守产品定义。
main使用不同且更明确的四个复products：LWA_EPIC.py:930-932标[xx,xy,yx,yy]，:1146表达式b(p/2)*conj(b(p%2))，不受上述UU公式影响。
phoenix Python epic_utils.py:205-208与初始本地:347-350仍用FITS STOKES轴-5,-6,-7,-8（XX,YY,XY,YX），但GPU最后两plane是Re/ImXY拆分而非完整XY/YX复值；这是继承的输出语义/元数据缺口，不能称四个标准Stokes。main按复相关写出，是不同格式，不应混为一谈。

六、GCF与correction的算法及问题归因
phoenix/offline：
- MOFF_correlator.hpp:277-282按频率GetAEff产生sqrt(aeff)*10 decimeter纹理宽度，再ProlateSpheroidalToTex2D。
- cu_helpers.cuh:280-346 ComputeGcfElements在每个天线/频道/像素做texture数值积分并把每天线kernel归一化sum1；界外像素贡献0。其频率位置/核支撑已考虑频道。
- MOFF_correlator:306-314先更细support和delta/oversample计算，求平均kernel再生成correction；随后重建原support GCF给电场grid。
- cu_helpers:359-385 ComputeAvgGriddingKernel对所有stands各cell atomicAdd，再除kernel总和。
- py_funcs.hpp:302-305说明correction是每频道平均kernel的平方ifft。
- Python epic_utils.py:330-377在M=N*oversample网格嵌入平均核，np.fft.ifft2，中心裁成N²，交换xy匹配GPU转置输出，|.|²后取倒数。
- fft_dx:271-274所有积累products乘correction。它应是位置依赖的平均gridding illumination校正，而不是常数增益。
继承问题：
1. MOFF_cu_handler.cu:131未给extern shared antenna_sum动态共享内存；:151 cudaMalloc之后未置0即atomicAdd，这是phoenix/offline共同问题。本地补launch sharedbytes和cudaMemset是在修复这两个问题。
2. 平均核对所有编译stands算，未根据有效phase、bad antennas、PAD有效性加权。原256LWA也存在masked antennas仍计平均的近似问题；本地16有6PAD后更显著。
3. gridder.cuh:511/540读gcf_grid_elem的channel_idx=blockIdx.x，而fft_dx.cuh:167天线坐标/相位/correction用blockIdx.x+chan_offset。nstreams>1时后续stream重复第一段GCF。这也是两个上游相同，不是本地新改。
4. Python get_correction_grid的两次np.fft.fftshift没有axes，连频道轴一起移；两次同长度频道shift对偶数nchan可抵消，对奇数未必恒等；属于上游继承的需验证边界。fix应明确axes=(1,2)，并保护结果兼容。
本地回归：
- 初始本地 epic_utils.py:558-561在归一化ifft2功率与float32 eps=2^-23比较。对于非负sum1核，最大功率<=1/M⁴；M64已有5.96e-8，M1283.73e-9，M2562.33e-10，均小于eps，因此整图倒数截成8388608。防NaN目的可理解，但毁掉空间correction。
- 主审已读当前repo/build的corr_grid_arr.npz，shape=(128,64,64), min=max8388608，支持现存产物确实常数化；不可归咎上游，它们是np.reciprocal直接倒数。
本地其他修改：
- 纹理ceil且>=1，并取与原当前宽度max，避免小AEff变0，但也更改频率切换只增不减和CLI aeff的有效性。
- 坏kernel改delta兜底和float中转类型是防坏数/编译的修改，不能替代物理校正验证。
main ant_extent=1(:849)，phases kernel含电缆校准(:939-964)，没有同名平均GCF反卷积校正链；因此“照main恢复correction公式”不适用。
